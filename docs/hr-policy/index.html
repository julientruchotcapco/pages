Solution blueprint

A retrieval-augmented generation (RAG) assistant that answers employees' HR questions only from approved, versioned policy documents. HR Admins curate the knowledge base and follow up on conversations employees pass to them; every answer and every change to the knowledge base is traceable.

GroundedAnswers cite policy excerpts; no excerpt above the relevance threshold means no LLM call and a referral to HR.
Human in the loopUploads are staged, diffed and reviewed chunk by chunk before anything reaches the vector DB. Sensitive, unanswered or poorly rated questions can be passed to the HR team.
Learns from feedbackEmployee ratings on similar questions re-rank policy passages and steer the prompt; comments never reach Claude.
TraceableEach answer stores the retrieval scores, prompt, model and token usage; each policy change stores who, what and the content hash.
Self-containedOne npm install: database, vector search and embedding model run in the Node.js process. Only answer generation calls an external API.

Flow 1 · Policy ingestion (HR Policies Admin)

  1. MatchThe file name is normalised to a policy key (version numbers and FINAL/DRAFT removed). If it matches a stored policy, the admin confirms "new version" or "separate policy (v1)".
  2. Extractunpdf (pdf.js) or mammoth turns the file into text; tables become Markdown rows. Scanned PDFs without a text layer are rejected.
  3. ChunkSplit at headings (max 1,500 characters); each chunk keeps its heading path. Tables stay together or repeat their header row.
  4. EmbedHeading path + text are embedded locally into normalised 384-dimension vectors.
  5. ReviewLine diff against the active version, chunk and vector preview, editing, and a retrieval test, all on the staged copy.
  6. SaveRe-embeds the final chunks, then one transaction deactivates the old version and inserts the new document and chunks. Logged as policy.committed.

Flow 2 · Question answering (Ask HR)

  1. RequestQuestion, recent conversation, employee profile, leave usage, and that employee's structured documents and payroll records.
  2. RetrieveThe last two questions are embedded; pgvector cosine similarity and PostgreSQL full-text rank are fused with Reciprocal Rank Fusion, then nudged by ratings of answers to similar questions (same location, similarity ≥ 0.8) that cited each chunk. Top 6 chunks, active versions only, restricted to Global policies and those tagged with the employee's location (from the user directory). Policies without a jurisdiction are never searched.
  3. GateIf no chunk reaches similarity 0.25, a fixed "not found, contact HR" reply is returned without calling Claude.
  4. GeneratePolicy answers remain grounded in cited excerpts. Personal document/payroll answers use server-fetched records for the selected employee; vector-retrieved templates support document guidance. Personal records are redacted from saved chat prompts. All payroll figures and generated files are synthetic.
  5. Cite[n] markers are mapped back to their source chunks, policy versions and scores.
  6. TraceA chat (or chat.error) event stores the full trace; its ID links the answer to the Audit trail.

Flow 3 · Feedback and handover to the HR team

  1. RateEach grounded answer asks "Was this answer helpful?". Thumbs down asks for optional reasons and a comment. Stored in feedback with the question embedding and the cited chunks; logged as chat.feedback.
  2. SuggestThe answer offers "Pass to the HR team" when the topic is sensitive (keyword check or Claude's flag), when no policy covers it, when similar answers were mostly rated unhelpful, or after a thumbs down. "Talk to the HR team" is always available.
  3. PassThe employee adds an optional message and a contact preference. The conversation is stored in handovers, not in the audit trail, so Support Admins cannot read it.
  4. NotifyHR Admins see a bell in the user menu and a count on Notifications while items are unaddressed.
  5. AddressAn HR Admin records how they followed up (1-1 conversation, email, Teams message, ...) and notes. Both are required.

Versioning

  • A new policy starts at v1. Saving a reviewed upload or edit creates the next version and makes it active.
  • Older versions remain as history. Only the latest version can be edited or deleted.
  • Deleting the active version reactivates the highest remaining version.
  • Save is refused (409) if the active version changed after staging.

Simulated systems

  • Synthetic, deterministic data relative to the seeding date. On each start, missing seed users are re-added, and seed users without leaves or timesheets get theirs.
  • Records are deactivated, never deleted, and every change is written to the audit trail.
  • Only Support Admins can manage them. A Support Admin cannot deactivate their own account or change their own access, and the last active Support Admin and HR Admin cannot be deactivated or demoted.

Security, privacy & data flow

  • Leaves the machine: the question, recent conversation, employee profile, that employee's structured document/payroll records and retrieved excerpts/templates are sent to Claude over TLS. Corporate root certificates are trusted via --use-system-ca.
  • Stays local: uploaded files, template and policy files, embeddings, the database and the audit log. Personal records are omitted from persisted chat system prompts.
  • Prompt injection: policy text and employee context are passed as delimited reference data, and the model is told to ignore instructions inside them.
  • Input limits: 10 MB per file, file-type allow-list, length caps on all fields, parameterised SQL, and no internal error details returned to the browser.
  • Access: the server checks the selected persona on every protected API: HR Admins only for policy admin, feedback, notifications and the full audit trail (everyone else sees only their own Ask HR exchanges); Support Admins only for the simulated systems and configuration.
  • Handover privacy: conversations passed to the HR team are kept out of the audit trail. Chat traces in the audit trail still include questions, so audit access should be limited in production.
  • Feedback privacy: only counts and reason codes of similar ratings reach the prompt; free-text comments are shown to admins only.
  • Menus: pages and menus a persona cannot use are hidden. This is a demo role switch, not authentication.

Prototype limits → production path

  • Demo personas → SSO (OIDC/SAML) with role claims from the identity provider.
  • Simulated user, leave and timesheet tables → read-only integrations with the real HRIS, LoA and timesheet systems.
  • Embedded single-process PGlite → managed PostgreSQL with pgvector, an HNSW index and backups.
  • In-memory staging → a persisted draft table, so reviews survive restarts and multiple instances.
  • Text-layer PDFs only → an OCR step for scanned documents.
  • Mutable audit table → append-only or WORM storage with a retention policy.
